## Part 1 — The machine story (why this computer needed setup)

Work happened across **two ZCode sessions on a Windows 11 machine** (`C:\Code\Lawleit`,
Git Bash shell), both worked late-night. That machine had **never run this project
before**, so session 1 bootstrapped everything:

- **No Node.js existed on the machine** — installed v24.19.0 LTS via
  `winget install OpenJS.NodeJS.LTS`. New terminals get it on PATH automatically; the
  session that installed it had to `export PATH="/c/Program Files/nodejs:$PATH"` manually.
- **Dependencies were never installed** — `npm install` in both `app/` and `backend/`.
- **A Windows bug was found and fixed**: `app/scripts/dev-all.mjs` spawned `npx`
  directly, which is `npx.cmd` on Windows and crashes with ENOENT. Fixed to launch Vite
  through `process.execPath` + `node_modules/vite/bin/vite.js` (cross-platform; commit
  `256eb6b`). Without this fix, `npm run dev:http` does not start on Windows.
- **Git identity was never configured** on that machine — set repo-locally (NOT
  `--global`) to the owner's existing GitHub identity (`ifreakingampsv`
  `<pseshanthvishal29@gmail.com>`), taken from the repo's own commit history.
- **No local Postgres and no Docker.** The production backend needs a hosted
  `DATABASE_URL` (Supabase/Render) which only the owner can provide (see Part 6).

**Two-machine workflow:** the owner develops on (at least) two computers. The OTHER
machine finished V1 and pushed it; this Windows machine pulled 12 commits to sync
(`git pull --ff-only origin main` — see `git log` around `2296b0b..2379622`). Rule of
thumb that has worked: **pull before starting work, commit locally per ticket, and the
owner decides when to push** (push = deploy, see Part 4).

**Harness quirks encountered on this setup (relevant to any agent):**

1. **Only ONE background subagent may run at a time** on the owner's plan — a second
   concurrent dispatch fails fast with "user concurrency limit exceeded". Serialize, or
   do the work inline.
2. **Long-running background agents were killed twice by the provider** ("Captcha
   verification request timed out") after ~5 hours. Resume via SendMessage with a
   precise state summary worked once; the second time the work was finished inline.
   Lesson: checkpoint state in commits and ticket checkboxes so any process can resume.
3. **In-app-browser locator clicks stall on this React app** (role-based `click()`
   times out even on snapshot-proven buttons). What works: `locator.evaluate()` with
   `scrollIntoView` + `getBoundingClientRect` to get viewport coordinates, then a
   coordinate click via `tab.cua.click`. Text `fill()` via locators works fine.
4. **Backend tests MUST run without `DATABASE_URL`** (see the safety note in Part 4).
5. Some repo files have CRLF endings (Windows) — patch scripts with `\r?\n`-tolerant
   matching or the Edit tool, not naive string replace.

## Part 3 — What this feature actually does (plain language, traced)

The problem: a law firm using Lawleit could *record* money it received, but couldn't
*ask* for it. Every invoice meant a phone call, a bank-transfer chase, and manual
bookkeeping.

The fix, traced through a real (verified) example — Ishaan Roy owes the firm ₹18,000 on
overdue invoice INV-1039:

1. **One-time setup (the firm owner):** In Settings → *Payments gateway*, the owner
   pastes the firm's own Razorpay API keys. They are encrypted and never shown again.
   This is the owner's job alone — staff must never be able to repoint where the firm's
   money lands. (Getting that Razorpay account in the first place is real-world work —
   see Part 6.)
2. **Collecting (any staff member):** The lawyer opens invoice INV-1039, clicks
   **"Create payment link"**, and Lawleit — speaking to Razorpay with the FIRM's
   credentials — produces a hosted checkout link for exactly ₹18,000. Two clicks share
   it: **Copy**, or **WhatsApp** (opens a chat with a prefilled payment message).
3. **The client pays:** Ishaan opens the link and taps **UPI** on a familiar checkout
   page. The money moves from his bank to the FIRM's bank, straight through Razorpay.
   Lawleit's servers never see or hold a rupee — which is what keeps a solo-founder
   SaaS out of India's payment-aggregator compliance regime (ADR-0006).
4. **The books update themselves:** Razorpay notifies Lawleit's webhook. The server
   checks the cryptographic signature, records the payment through the same code path
   a bookkeeper's manual entry uses, and the invoice flips to **Paid**. If the client
   pays only part, the invoice follows the exact same rules as a manual partial record
   (a draft stays a draft until fully paid).
5. **When the notification gets lost:** the API sleeps on Render's free tier; a webhook
   can arrive while it's waking. Razorpay retries — and anyone in the app can also hit
   **"Sync"**, which asks Razorpay directly "did this get paid?" and repairs the books.
6. **Trust money stays sacred:** client money held in trust can ONLY be entered
   manually. Gateway collections are structurally barred from touching the trust
   ledger.
7. **The portfolio demo:** a visitor on the Demo Version does all of this with fake
   money — a simulated checkout page at `/pay/:id` — and "Reset demo data" wipes it.

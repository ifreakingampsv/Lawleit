## Comments

- (agent, post-build) **Route surface** (routes/invoices.ts, per contract — there is NO create-from-entries endpoint in the contract: the client assembles `lines` from unbilled entries and POSTs the invoice, mockAdapter/httpAdapter/server.mjs all agree): GET /invoices (newest-first, lines embedded), GET /invoices/:id, POST /invoices → 201, PATCH /invoices/:id, DELETE /invoices/:id → 204. Every firm member manages invoices (practice data, no owner gate). Missing/foreign/soft-deleted ids are uniformly 404 "Invoice not found"; malformed uuid params 400.
- (agent, post-build) **DDL (migration 0006, drizzle-kit generated)**: `invoices` (firm_id FK+idx, case_id FK+idx, client_id FK unindexed — every listing page joins clients client-side, no server query path; `number` text with partial unique `(firm_id, number) WHERE deleted_at IS NULL`; `status` text default 'draft', contract vocabulary draft/sent/overdue/paid; `issue_date`/`due_date` date mode:string; notes; soft-delete stamps); `invoice_line_items` (firm_id FK+idx, invoice_id FK+idx, `position` int = client's send order — same-instant inserts share one now() so a sort key is required; description; `quantity` double precision — the contract's quantity is a JS number (hours = minutes/60) and binary64 round-trips byte-exact; `rate`/`amount` bigint paise; `kind` text time/expense/flat; **V2 GST seam present from day one: `tax_rate` numeric(6,2) NULL + `tax_amount` bigint NULL, never written by V1 code**); `invoice_number_counters` (PK firm_id, last_value int). **Deliberately NO total columns on invoices** — the contract's Invoice carries no totalAmount/amountPaid/balance ("check the model … mirror EXACTLY" resolves to: derived); the server-side total lives in `invoice_line_items.amount` (round(quantity×rate), computed server-side on every write, client-sent amounts/ids stripped) and the invoice total is Σ(amounts) via `InvoicesService.totalPaise(firmId, invoiceId)` (404s on unknown) — **ticket 14's roll-up must read that seam, not re-derive from float quantities**. Lines are a value set: a PATCH carrying `lines` hard-swaps the rows (no per-line soft delete — the invoice's deleted_at governs visibility).
- (agent, post-build) **Numbering**: copied the ticket-10 counter pattern as a separate `invoice_number_counters` table (one-line justification for the choice: the INV sequence has no year dimension to key on — the reference's is one running per-firm count — so generalizing case_number_counters would force a discriminator column onto a differently-keyed sequence; two tables keep both counters' atomic upserts identical in shape). Atomic INSERT … ON CONFLICT DO UPDATE inside the create transaction; two parallel creates get INV-0003/INV-0004 (pinned in the DB twin). Starts at INV-0001 — the reference's +1044 offset is demo-seed legacy, same rationale as the case counter's +50. Per-firm independent; numbers never reused after deletes (partial unique + monotone counter).
- (agent, post-build) **Invoiced-flag flip path (the ticket-16 handoff seam)**: `TimeEntriesService`/`ExpensesService` now expose `listUninvoicedByCase(firmId, caseId)` (live + uninvoiced + firm/case-scoped, newest first; malformed caseId 400, unknown case → empty list — a selector leaks nothing) and `setInvoiced(firmId, ids, invoiced)` (firm-scoped bulk flip returning the moved count; cross-firm/soft-deleted ids silently inert) — implemented in BOTH the Drizzle bindings and the in-memory fakes, DB-twin covered in time + expenses. **Not wired into POST /invoices or DELETE**: the contract's InvoiceLine carries no source-entry reference (no entryId), so creation cannot know which entries a line came from, and the reference/mock mark nothing — mirroring them means invoice CRUD leaves the flags alone. The flags remain server-managed (never client-patchable); the future invoice-builder UI (or ticket 14 if payments need it) flips them through this seam.
- (agent, post-build) **Status rules enforced here vs ticket 14**: PATCH accepts the contract vocabulary only (400 "Status must be draft, sent, overdue, or paid"); transitions are free within it (the reference Object.assigns; the UI's Send / Mark-as-paid buttons drive draft → sent → paid directly). "overdue" is a stored vocabulary value (the seed carries it), NOT derived at runtime — neither mock nor reference derives it. **Ticket 14 owns the payment roll-up**: status = paid when Σ(non-failed payments) ≥ total; partial payment keeps a draft a draft (draft → sent only when the invoice was already sent) — the parity fix pinned in smoke ("partial payment keeps invoice sent"); use `totalPaise` for the total. Reference PATCH/DELETE gate nothing by status: paid invoices stay patchable and deletable — pinned by tests here too.
- (agent, post-build) **Deltas vs the reference (deliberate hardening, observable behavior unchanged for valid clients)**: client-sent `number`/`id`/line `id`/line `amount` are stripped or ignored (the reference stores them verbatim; DB rows need real UUIDs and the server owns the money); quantity/rate/kind/description-length/line-count(≤200) validation 400s the reference never had (the UI only sends valid lines); clientId/caseId are existence-checked uuid FKs ("" renders like the reference's empty string); issued/due are server-stamped at create (today / today+30, the reference ignores client values there too) but patchable. `ApiInvoice` responses are byte-shape compatible with the mock adapter: {id, number, clientId, caseId, issued, due, status, lines[{id, description, quantity, rate, kind}], notes?} — position/amount/tax columns/soft-delete stamps whitelisted out.

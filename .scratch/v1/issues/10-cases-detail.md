## Comments

- (agent, post-build) **Case detail = contract surface only; there is no aggregate endpoint.** docs/API_CONTRACT.md defines GET /cases/:id as `getCase(id)` → the case entity, full stop, and neither `LawleitApi` (api.ts) nor httpAdapter has a caseDetail-style method. The UI's detail page (app/src/sites/app/pages/CaseDetail.tsx) composes the "aggregated matter view" itself: `api.getCase(id)` + plain `listContacts/listTasks/listTimeEntries/listInvoices/listDocuments` calls, client-filtered by caseId. So the backend implements exactly the contract surface and nothing additive; the detail page lights up as tickets 11–13 land those list endpoints. (Checkbox ticked in that sense — the aggregate the UI expects is per-entity lists, all contract endpoints.)
- (agent, post-build) **Number assignment.** Reference format is `` `2026-${String(db.cases.length + 50).padStart(4, "0")}` `` — count-based with the year hardcoded, which reuses numbers after deletions (hard delete shrinks the count) and collides under concurrent creates. Production mirror: `${currentYear}-NNNN` (the contract's example `2026-XXXX` is this year's rendering of the format) from a `case_number_counters` row per **(firm, year)**, reserved by one atomic `INSERT … ON CONFLICT DO UPDATE` inside the create transaction — the counter row's lock serializes concurrent creates (route test fires 5 parallel POSTs; DB twin repeats it on real Postgres), sequences are independent per firm and per year, and no number is ever reused after a (soft) delete. Production has no seed, so the demo's +50 offset clears itself: the first case is `-0001`. Client-sent `number` is stripped by the zod schema and the patch type (tested: `number: "9999-1234"` on create, sneaky patches — both ignored). `trustBalance` is server-managed the same way (always 0 until the trust ledger owns it).
- (agent, post-build) **Filters mirror the reference exactly.** `?status=` is exact equality — an unknown status is an empty list, not an error (no vocabulary check at the query layer; create/patch DO validate the vocabulary as 400s). `?q=` is a case-insensitive substring over the space-joined `` `${number} ${title}` `` — implemented as `position(lower(q) in lower(number || ' ' || title)) > 0`, so a query may span the number/title boundary and `%`/`_` stay literal (the reference's `.includes()`); both behaviors pinned by tests.
- (agent, post-build) **Deletion rules: nothing blocks a delete.** The contract (204, no error cases) and the reference (plain filter) gate nothing — dependents (invoices/trust/tasks) are tickets 11–13 and get to decide their own back-references. Delete is a soft delete per the baseline convention: row stays with `deleted_at` stamped, reads drop it, repeat delete and foreign delete are 404 "Case not found", and the counter never walks back (deleted case's number is never reissued — tested).
- (agent, post-build) **Defaults + validation parity with the reference, with the production money unit.** Empty-body create lands on: title "New matter", clientId "" (stored as a nullable FK, rendered as "" in the contract shape), practiceArea "General", stage "intake", status "open", openDate = server-stamped today (a client-sent openDate is ignored on create, exactly like the reference; patch-only afterwards), description "", trustBalance 0, leadAttorney = the firm's first user (the reference's `db.users[0]` analog). billableRate defaults to 300000 — the mock adapter's paise default (₹3,000/hr); the reference's 300 is its stale dollar-era value, the paise convention wins. Validation 400s (service constants, tested verbatim): status/stage vocabularies, client id uuid shape ("Invalid client id") + unknown client within the firm ("Client not found"), attorney uuid shape, ISO YYYY-MM-DD dates, non-negative-integer rate, length caps. Failed creates consume no numbers. Status transitions: the contract defines no transition table for cases (unlike tasks' todo → in_progress → …), so open/pending/closed move freely — pinned by tests.
- (agent, post-build) **Permissions + isolation.** Cases are practice data: every firm member creates/patches/deletes (no owner gate — the contract and reference gate nothing here, same call as contacts, unlike POST/PATCH /users; invited-attorney flow tested). Cross-firm: another firm's case 404s identically on GET/PATCH/DELETE and leaks nothing; lists and ?q= searches never cross the boundary; counters are per-firm (both firms' first case is `-0001`). Schema: `cases` (uuid pk, firm_id FK not null + index, client_id nullable FK to contacts + index, bigint-paise money columns, date columns as `date mode:string`, timestamptz stamps, deleted_at, partial unique `(firm_id, number) WHERE deleted_at is null` as the race backstop) + `case_number_counters` (pk (firm_id, year)); `lead_attorney_id` deliberately FK-less, mirroring the reference's soft links.

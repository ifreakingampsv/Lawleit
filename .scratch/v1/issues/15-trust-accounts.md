Every firm member reads the ledger (practice data, no owner gate). Anonymous 401; no-database 503 envelope.
- (agent, post-build) **DDL (migration 0008_boring_the_anarchist, drizzle-kit generated)**: `trust_transactions` (firm_id FK+idx; **`client_id` NULLABLE uuid FK+idx** — null is the unattributed bucket the reference stores as `""` when a trust-flagged payment names no client, entries still append and render `""`; **`case_id` NULLABLE uuid FK+idx** — the reference's `invoice?.caseId ?? ""`, null for unlinked deposits; `date` date mode:string; `description` text default ''; **`amount` bigint SIGNED paise** (+in/−out, the contract's own comment); **`balance_after` bigint** — the running per-client balance stamped by the append; **`seq` bigserial** — DB-only insertion-order stamp, whitelisted out of the API; `created_at` stamp). **APPEND-ONLY, a deliberate departure from the baseline soft-delete convention: NO updated_at, NO deleted_at, and the repository seam exposes no update/delete path at all** — a ledger never rewrites history; a mistaken entry is corrected by a contra entry (the accounting practice), never by editing the past. No partial unique indexes (no unique-ish business fields). Schema header comment documents the departure in place.
- (agent, post-build) **Serialization design for concurrent appends — per-client advisory lock + seq, NOT the reference's approach** (one-line delta: the reference is a naive `reverse().find()` over a single-threaded JS array; a production read-then-insert races, and both appends would compute the same balanceAfter and FORK the chain — FOR UPDATE on the last row does not help either, because a concurrent NEW-row insert is invisible to the other transaction's statement snapshot). `DrizzleTrustRepository.append` (services/trust/drizzle.ts) runs `pg_advisory_xact_lock(md5("firmId:clientId") → 64-bit key)` inside the caller's transaction, then reads the client's latest `balanceAfter` and inserts the new row with `seq` from the bigserial. Same-client appends queue (each reads the predecessor the previous one committed); different clients never contend; the lock is xact-scoped (auto-release, no leak on rollback), and the hook path holds it for the remainder of the payment transaction (harmless — one lock, one waiter chain, no deadlock cycle). The lock also makes `seq` reflect true append order per client, which `listByFirm` and reconcile order by — deterministic where (created_at, id) is not (same-instant inserts, random UUID tie-breaks). The in-memory twin is atomic by construction: read-prev and push happen with NO await between, so a Promise.all interleave can never slip between them.
- (agent, post-build) **Balance rule + hook wiring (the ticket-14 hook is now WIRED)**: `backend/src/services/payments/service.ts`, inside `record()`'s `repos.transaction` callback after the roll-up, the marked block now does — when `payment.trustAccount` — `tx.trust.append({ firmId, clientId: payment.clientId, caseId: invoice?.caseId ?? null, date: payment.date, description: trustDepositDescription(invoice?.number ?? null), amount: payment.amount })`. The composition is byte-identical to the reference's appendTrust (description `Trust deposit — invoice INV-XXXX` / `Trust deposit — invoice (unlinked)`, em-dash and all); the running `balanceAfter = prev?.balanceAfter ?? 0 + amount` is computed by the repository INSIDE the same transaction, so the payment, the roll-up and the ledger entry commit or roll back together. The payments route test now pins the ledger consequence of its unlinked trust deposits; the trust suite pins the linked + unlinked + case-linked entries.
- (agent, post-build) **Reconcile semantics (service-level, `TrustService.reconcile(firmId)`)**: walks the firm's whole append-only history in `seq` order, keeps a running Σ per balance bucket (null client = its own bucket, the "" bucket), and reports `{ ok, entries, clients, mismatches[] }` where each mismatch carries `{ id, clientId, date, seq, stored, computed }` — computed from the amounts ALONE, so a corrupted balance is detected exactly where it happened and untampered neighbors report nothing. **Tamper-detection proof**: the route test manually corrupts one `balanceAfter` in the in-memory store (+999999 on a −200000 entry) → `ok:false` with that single entry, `computed: 300000`; the DB twin does the same via a raw `UPDATE ... SET balance_after = 999999` on real Postgres → identical report — and after an operator's raw-SQL correction agrees with the history again, reconcile goes green (it is a pure recomputation, never a repair; the service exposes no write path but append). **The contract defines no reconcile HTTP route and the ticket's "reconcile endpoint" is therefore implemented at the service seam** — tested directly, callable by an ops job, and V2 can surface it without a V1 contract change.
- (agent, post-build) **TrustService.append (service seam, no HTTP route)**: deposits (+) and disbursements (−) in one transaction with the same running-balance rule — the deposit→withdraw→deposit chain tests need a withdrawal writer, V1's contract exposes none, and V2's retainer trust model hangs off exactly this seam. Validation before anything is written: signed non-zero integer amount with the payments |amount| ≤ 1e9-paise cap (400), real-calendar-day ISO date defaulting to today (400, the reference's `today()`), provided clientId must be a uuid (400) and a LIVE in-firm contact (400 "Client not found", the payments rule — a foreign or soft-deleted client writes nothing anywhere). caseId stays a soft link (the cases.lead_attorney_id pattern; the hook passes the invoice's FK-guaranteed case).
- (agent, post-build) **Soft-deleted clients (per contract)**: the contract has no client-death semantics for trust, so the ledger follows money reality — a soft-deleted client's HISTORICAL entries still list, still reconcile, still count (the deletion must never rewrite or hide money history; the reference/mock, which know no soft deletes, list everything too), while NEW entries are impossible: a trust-flagged payment naming a deleted client 400s "Client not found" through the hook (ticket 14's live-contact validation) and via the service seam — pinned in both suites.

## Comments

- (agent, post-build) Route surface per contract, mounted inside the protected plugin (401/503 envelopes inherited, every member manages leads — practice data, no owner gate): `GET /leads` (newest first, unshift parity), `POST /leads` (201; reference defaults — "New lead", empty email/phone, source website, stage new, practiceArea "General", value 0; notes absent unless sent), `PATCH /leads/:id` (only sent fields move; free stage transitions, no transition table — a direct jump to "converted" or back out of it is allowed, like the reference's Object.assign), `DELETE /leads/:id` (204/404, soft delete — the row stays, `deleted_at` stamped), `POST /leads/:id/convert` (201 `{ lead, contact, case }`). There is NO `GET /leads/:id` — the contract mounts none and the pipeline board reads the list.
- (agent, post-build) Migration 0005 (`drizzle/0005_brave_redwing.sql`): `leads` (uuid pk, firm_id + index, name/email/phone/source/stage/practice_area text, `value` bigint integer paise default 0, nullable notes, `activity` jsonb default `[]`, nullable `converted_case_id`/`converted_contact_id` FKs, timestamptz stamps + `deleted_at`) and `lead_stage_history` (firm_id, lead_id FK, from_stage, to_stage, `changed_by` uuid — the no-FK soft-link pattern, `at` timestamptz; append-only, so no updated_at/deleted_at). The links are DB-only traceability — the contract's Lead shape doesn't carry them, so the API mapper whitelists them out (the events.`source` seam treatment). No unique-ish business fields → no partial unique indexes.
- (agent, post-build) Conversion = ONE `repos.transaction`: load lead (firm-scoped, live) → 404 "Lead not found" / 409 "Lead already converted" (exact envelope, the mockAdapter parity fix) → create contact (type client, lead's name/email/phone, empty address/caseIds) → reserve `YYYY-NNNN` from the same per-firm-year `case_number_counters` POST /cases uses (the reference's `assignCaseNumber()`, hardened in ticket 10) → create case (title from payload or `<name> — <practiceArea>`, clientId = new contact, stage intake, status open, openDate today, leadAttorney = firm's first user, billableRate 300000 paise, trust 0) → link the case into contact.caseIds → update lead (stage converted, activity entry, links) → one lead_stage_history row. Only `title`/`description` are read from the convert body (the reference's read surface); everything else is stripped, so a sneaky payload cannot set case stage/status/number/rate. Double convert creates nothing (asserted: case count stays 1).
- (agent, post-build) Stage-history mechanics: the contract makes "stage moves append to `activity`" a server responsibility — the reference/mock instead let the client overwrite the array wholesale (the UI literally sends its own `activity: [{ text: "Moved to X" }]` on every stage move and Object.assign replaces history). The production backend treats `activity` as server-managed: client-sent `activity` is stripped from create/patch payloads, and the server prepends `Moved to <stage>` on an actual stage change (newest-first, same position and wording the reference's conversion entry uses — the UI-visible timeline reads the same as what it tried to write itself) plus one lead_stage_history row in the same transaction (from → to, actor, instant). Re-sending the current stage records nothing. Conversion prepends `Converted to case <number>` exactly like the reference. History outlives the soft delete (audit trail, not a live view); no contract endpoint exposes it — it's the queryable record behind the jsonb log.
- (agent, post-build) Deliberate hardening deltas, observable behavior unchanged for valid UI flows: type vocabularies (stage: new/consult scheduled/contacted/fee agreement/converted/lost; source: website/referral/call/ads/walk-in) and value (non-negative integer paise, 1e9 cap) get server-side 400s the mock never had; length caps on name/email/phone/practiceArea/notes; zod strips server-managed fields (id/firmId/createdAt/activity/converted*Id) so whole-entity saves keep working. No email format check — a lead is not a login key (the contacts rule). Soft delete behind identical 204/404s.

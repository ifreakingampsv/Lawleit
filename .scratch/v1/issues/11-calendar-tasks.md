## Comments

- (agent, post-build) Datetime decision — the contract is the authority, and it deals in ISO calendar DAYS, not instants, on both surfaces: `CalendarEvent.date` is an ISO day with `start`/`end` as "HH:MM" strings (types.ts), the contract's Conventions say "Dates are ISO YYYY-MM-DD (days)…", and mock + reference filter `GET /events` with day-string comparison. So `events.date` and `tasks.due_date` are `date mode:string` columns and `start`/`end` are text (a `time` column would read back "11:00:00" and break byte-shape parity with the mock). The checkbox's "stored UTC" therefore lands on the bookkeeping stamps only (`created_at`/`updated_at`/`deleted_at` timestamptz); the contract carries no instant field on either surface, and `Task.createdAt` — an ISO day in the contract — is the baseline timestamptz stamp collapsed to its UTC date part by the API mapper. The `source` seam is built NOT NULL DEFAULT 'manual' (the build note resolves the ticket's "nullable" wording to nullable-free): never client-settable, never in the API shape, DB default proven even for raw inserts by the events DB twin — exactly the shape a V2 cause-list importer needs to diverge from. Deliberate hardening deltas (invisible to valid clients): zod strips server-managed fields (id/firmId/source/createdAt) from whole-entity saves; soft deletes behind identical 204/404s; type/priority/status vocabularies, ISO-day and HH:MM shapes, uuid shapes and length caps get server-side 400s the mock never had; case links are existence-checked (unknown or soft-deleted case → 400 "Case not found") because `case_id` is a real FK where the mock/reference would store a dangling id. Permissions: practice data — every firm member manages both surfaces (no owner gate), matching contract + reference.
- (agent, post-build) Parity spot checklist — UI action vs mock adapter, verified in-memory (route tests bind the in-memory repos): CalendarPage new event (title/date/start/end/location/type/color) → 201; empty fields land on the reference defaults ("New event", today, 09:00–10:00, meeting, #4B4ACF, attendeeIds []); list order matches both sides — events PUSH (insertion order, oldest first), the one deliberate exception to the unshift-newest-first rule contacts/cases/tasks follow. `GET /events?from=&to=` is inclusive on BOTH ends, bounds optional, malformed bounds 400 before any SQL cast. TasksPage new task (title/dueDate/priority/caseId) → status defaults todo, assignee defaults to the firm's first user (the reference's `db.users[0]`, firm-scoped here); completion is Dashboard's checkbox / TasksPage `setStage` — both are `updateTask(id, { status })`, and transitions move freely across todo/in_progress/blocked/done (the contract's "status flow" documents the UI flow, not a server-enforced machine — the mock's Object.assign semantics, pinned by tests). Deletes: 204, leaves the list, repeat delete 404s. Byte-shape parity: unset nullables (caseId, location, allDay, reminders, description) drop from responses; firmId/source/bookkeeping never appear.
